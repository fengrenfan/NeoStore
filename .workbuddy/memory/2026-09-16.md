## 更正 09-15 那条错误结论：`request.cookies.get()` 其实是好的

顺着"继续"把同类陷阱审了一遍，结果推翻了昨天写下的两条结论之一。

**事实**：在改前的线上镜像上直接测 `/`（带 `Cookie: neostore_locale=en` +
`Accept-Language: zh-CN`）→ **307 到 `/en`**。这条链路当时用的是
`request.cookies.get(LOCALE_COOKIE)?.value`，而它工作正常。也就是说：

- `request.cookies.get()` **能**读到入站 cookie，standalone Next 15.1.6 下没问题。
- 昨天区域那次失败的**唯一**根因是 `REGION_COOKIE` 从 `"use client"` 的 `session.ts`
  导入后运行时成了 `undefined`，于是 `request.cookies.get(undefined)` 永远不匹配。
  当时两次调试（先试 `request.cookies.get`、后试自写 `getCookie`）**都带着这个未定义的
  name**，所以两次都失败，把结论冤枉到了框架 API 头上。

**改动**：删掉 middleware 里自写的 `getCookie()`（正则解析原始 `Cookie` 头），
两处（region / locale）统一回到框架的 `request.cookies.get(name)?.value`；
把 middleware 的文档注释改写成真相，并留了一条"别再重复踩"的调试说明。

**验证**：本地 tsc exit 0 → 服务器 `docker compose build storefront` + 重建 →
- `/` + `Cookie: neostore_locale=en` + `AL=zh-CN` → `/en`（cookie 优先于 AL）
- `/` + `Cookie: neostore_locale=ja` + `AL=en-US` → `/ja`
- 无 cookie：`AL=ja` → `/ja`；无 AL → `/zh-CN`（默认）
- 区域回归（本次改动的关键点，因为换了 cookie 读法）：`Cookie: neostore_region=cn`
  访问 `/en/products` → **307 → `?region=cn`**；jp 同理
- `?region=` 四区定价仍正确：us `$19.99` / cn `CN¥134.47` / eu `€17.33` / jp `¥3,100`
- 四个路由 200；真实浏览器 `scripts/storefront-check.cjs https://store.xiaodigua.shop` **15/15**

**教训（真正该记的那条）**：排查 middleware 读不到 cookie 时，先把 cookie **名字**
打印出来确认它不是 `undefined`，再去怀疑框架 API。服务端代码里任何从 `"use client"`
模块导入的**值**都可能是 `undefined`——这条是昨天第 3 点，是对的，而且它是唯一的原因。

**顺带一个观察（非本次回归）**：种子数据商品图指向 `https://cdn.neostore.local/...`，
公网必然 `ERR_NAME_NOT_RESOLVED`。`ProductImage` 有 `onError` 降级（渐变块 + 首字母），
所以视觉上不炸；browser check 偶尔会因 `loading="lazy"` 的时序把它算作 failed request
（上一轮 `en` 跑法就报出来了，默认跑法 15/15 过）。换真图前不用管。

**新增技能**：`neostore-storefront-deploy`（本地改 → scp → build → recreate →
curl 矩阵 + browser check 的闭环）。

## 把 Neostore 接进服务器看门狗

服务器的「看门狗」是一个 bash 脚本，不是容器：

| 项 | 值 |
|---|---|
| 脚本 | `/home/ubuntu/server-watchdog.sh`（700 ubuntu:ubuntu，**只在服务器上，无版本管理**） |
| 调度 | crontab `*/2 * * * *`（每 2 分钟） |
| 日志 | `/home/ubuntu/server-watchdog.log` |
| 发信 | `/home/ubuntu/alert-send.py`（可执行，被脚本 `-x` 判断后才调） |
| 状态 | `/home/ubuntu/alert-state`（冷却）、`alert-failures`（连续失败计数）、`alert-heartbeat`（心跳日期） |

**脚本结构**（改它之前先看懂）：
- 配置：`COOLDOWN=1800`（同容器普通告警最小间隔）、`FAIL_THRESHOLD=3`（连续失败升级严重）。
- 目录变量：`COSMETICS_DIR=/home/ubuntu/app`、`BLOG_DIR=/home/app/blog/docker`、`STORE_DIR=/home/app/store`。
- 巡检清单是一段字符串：`SERVICES="<容器名>|<compose 目录>|<heavy>"`，逐行 `IFS="|" read`。
- 每个容器的处理：`missing` → `cd $dir && docker compose up -d`（整项目拉起）；
  `非 running` → `docker start`（`heavy=1` 且 `free -m` 可用内存 <400MB 时**跳过**，防 OOM 风暴）；
  `unhealthy` → `docker restart`；每次动作后 `check_result` 复核，失败计数 +1。
- 有动作就发普通告警邮件；连续 3 次拉不起来升级严重邮件；每天 09 点首轮发心跳汇总。

**本次改动**（备份 `server-watchdog.sh.bak-20260916`，新 md5 `487770c4f6959c0c530fd71990752784`，167→175 行）：
1. 头部注释 `cosmetics-shop & blog` / 「巡检 9 个容器」→ 加 neostore / **16 个**。
2. 加 `STORE_DIR=/home/app/store`，SERVICES 追加 7 个 `neostore-*`（**heavy 全给 0**，与 blog-* 一致；
   7 个都写成带 `-1` 后缀的真实容器名，compose 文件里有 `name: neostore`）。
3. **心跳里的 `docker ps | grep -E 'cosmetics|blog'` 也要同步加项目名**，否则心跳邮件里看不到它。

**验证**（决定性）：故意 `docker stop neostore-worker-1` → 手动跑一轮 → 日志
`neostore-worker-1 status=exited -> docker start` + `ALERT_SENT_OK` + `alert email dispatched`
→ worker 回到 `running`。即检测/拉起/发信三条链路对一个 store 容器都成立。
> 这次测试**真的发了一封告警邮件**（标题「【服务器告警】容器自动修复」），不是故障。

**还没覆盖（值得跟仁凡提）**：
- `quant-engine` / `quant-web` / `quant-backend` **一直就不在清单里**，看门狗从来没管过量化项目。
- 看门狗只看容器状态，**不探 HTTP**：caddy 起着但 storefront 返 500 / 区域定价坏掉这类
  「容器健康但网站不可用」的情况它发现不了。要真覆盖得加 `curl -f` 探活。
- 脚本没有版本管理（只有同盘的 `.bak`），服务器挂了就没了。
