## 新项目：NeoStore（轻量单店 DTC 跨境独立站）

用户确认的决策：单店 DTC 形态 / FastAPI + React / 先做通用多语言框架 /
方案 A 前端结构（Next.js 店面 + 独立 Vite 后台）/ PostgreSQL / 首期最小可用闭环。

设计文档已落地并提交：
`docs/superpowers/specs/2026-09-15-neostore-design.md`
git 已 init，首个 commit `60fd0bd`。

关键设计决定：
- i18n 用独立翻译表（`*_translation` + UNIQUE(entity_id, locale)），不用 JSONB 内嵌字段。
- 多币种：显式定价优先，缺失时按汇率换算兜底；换算结果按目标币种 decimal_places 取整。
- Region = 币种 + 语言集合 + 税率 + 可用支付方式的聚合。
- 金额一律 Decimal，计算收敛到 `pricing.calculate()` 单一入口。
- 库存用 `SELECT ... FOR UPDATE` 行锁 + reserved 预占防超卖。
- 下单接口支持 `Idempotency-Key` 防重复下单。
- domain 层禁止 import fastapi / 直接拿 Session，持久化走 repository 接口。

状态：**设计待用户评审**，评审通过后进入实施计划（M0–M4）。

### 今天踩到并修掉的真问题（都值得记住）

1. **冒烟测试被"陈旧数据库"骗过**：`smoke.sh` 原来删共享的 `smoke.db`，一旦删除没落地
   （被拒绝、残留 `-wal`、旧进程抱着旧 inode），本次运行就继承了上一轮的订单，
   于是 checkout 返回的是上轮那笔**已支付**订单，断言全在描述错误的世界。
   修法：每轮用唯一 `smoke-<pid>.db` + 断言"0 订单 3 商品" + 端口被占用时直接退出。
2. **时间戳时区**：SQLite 的 `DateTime(timezone=True)` 回来是 naive，浏览器把
   `2026-09-15T07:51:52` 当本地时间读，CST 下显示差 8 小时。加了 `app/core/serialization.py`
   的 `UtcDatetime`（`+00:00`），PostgreSQL 与 SQLite 行为一致。
3. **`docker compose` 里 `app.seed --if-empty` 这个参数并不存在**，argparse 会非零退出 →
   api 容器起不来。已删（seed 本身幂等）。
4. 沙箱内 npm install 会被文件系统 broker 拒绝 → `scripts/sandbox-fs-guard.cjs`（`node -r` 预加载，
   限制 mkdir/rename/symlink 并发）是唯一可行路径。

## 这台服务器构建镜像的两个大坑（下次直接照做）

**一、Docker Hub 直连不通，daemon.json 里的源一半是死的。**

- `/etc/docker/daemon.json` 写着 ustc / 网易 / 腾讯云内网三个源，但 **ustc 和网易
  早就停服了**，`registry-1.docker.io` 本身也不通（curl 超时）。构建会卡在拉基础镜像上
  十几分钟毫无进展，而且因为 `| tail` 缓冲，**看不到任何报错**——只有 `docker images`
  里什么都没有才能看出来。
- 可用的：**`mirror.ccs.tencentyun.com`**（腾讯云内网，200，最快）、
  `docker.m.daocloud.io`、`docker.1panel.live`、`hub.rat.dev`。
- **不要为此重启 dockerd**——机器上还有 blog / quant / cosmetics 三套在跑，重启会一起抖。
  改用「预拉取 + 打标签」：`docker pull mirror.ccs.tencentyun.com/library/<img>` 然后
  `docker tag` 成官方名，构建时就不再访问 registry。
- 需要的 5 个基础镜像：`postgres:16-alpine` `python:3.13-slim` `node:22-alpine`
  `nginx:1.27-alpine` `caddy:2-alpine`（`redis:7-alpine` 本来就有）。

**二、包源：apt 25 KB/s，pypi.org 直接不通。**

- `deb.debian.org` 从这台机器下载只有 **~25 KB/s**（装 build-essential 92 MB 要一小时）；
  **`pypi.org` 完全不可达**——也就是说后端镜像按原样永远不会构建成功；
  `registry.npmjs.org` 通，但只有 5.5 MB/s。
- 腾讯云内网源实测：pypi **55 MB/s**、npm 18 MB/s、debian 200。
  完整取值（写进 override）：
  - `APT_MIRROR: mirrors.tencentyun.com`（只给主机名，让 `/debian` 和 `/debian-security` 都命中）
  - `PIP_INDEX_URL: https://mirrors.tencentyun.com/pypi/simple/`
  - `PIP_TRUSTED_HOST: mirrors.tencentyun.com`
  - `NPM_REGISTRY: https://mirrors.tencentyun.com/npm/`
- Dockerfile 里做成 **build arg 且默认指向官方源**，服务器用 override 注入 →
  仓库保持可移植，不会把国内源焊死进代码。
- python:3.13-slim 是 Debian 13 (trixie)，apt 源在
  `/etc/apt/sources.list.d/debian.sources`（deb822 格式，`URIs:` 行），
  sed 替换 `deb.debian.org` 即可。

## storefront 生产构建挂了：三个真 bug

`next build` 在服务器上失败：`/sitemap.xml` 和三个 `/[locale]/cart` 各卡满 60 秒预渲染
超时、重试三次，整个构建连带挂掉。**注意这是这个前端第一次真正跑生产构建**——
之前的 smoke 用的是 dev server，所以问题一直藏着。

线索：`robots.ts`（同为静态路由、同样调 `siteUrl()`）构建正常，`sitemap.ts` 不行，
**唯一差别是后者 await 了一次 fetch**。

三个原因，都是真的：

1. **`cart/page.tsx` 是全 `(shop)` 下唯一漏了 `force-dynamic` 的页面。**
   其余四个（home / products / products\[slug\] / checkout）都声明了，
   `lib/server.ts` 的注释也白纸黑字写着「依赖它的路由都标了 force-dynamic」。
   购物车是 per-visitor（布局要读 cookie 定区域定价），本来绝不能预渲染成共享壳。
2. **构建期从没设过 `API_BASE_URL`。** compose 里的 `environment` 只在运行时生效，
   构建阶段没有 → 服务端 `baseUrl()` 落到公开地址，而生产环境那是**空字符串** →
   `fetch` 拿到相对路径 → 抛**裸 TypeError**，而 `tolerantDuringBuild` 只认
   `ApiError(NETWORK_ERROR)`，于是不兜底、直接把预渲染 worker 拖死。
   修法：Dockerfile 构建阶段 `ARG API_BASE_URL=http://api:8000`——
   解析不了的主机名会以「普通连接失败」的形式报错，那才是这个容错分支设计时的场景。
3. **`raw()`（`request()` 的兄弟，返回 Response）没做同样的错误归一化**，
   导致走 `raw()` 的 `getProducts`（sitemap 在用）根本没法被容错。
   现在它和 `request()` 一样把传输错误包成 `ApiError(NETWORK_ERROR)`。

修完后静态页生成从「卡死 180 秒」变成 **23 秒跑完 17/17**。

## admin 镜像构建失败：lockfile 被内网私服钉死

`npm ci` 稳定在 470 秒后报 `npm error Exit handler never called!`（两次都一模一样，
不是偶发）。**要看真因必须加 `--loglevel=http`**，日志里全是：

```
npm http fetch GET http://192.168.1.99:9090/repository/npm-group/...  attempt 3 failed with ETIMEDOUT
```

- `admin/package-lock.json` 里 **192 个 `resolved` 全指向 `http://192.168.1.99:9090/repository/npm-group/`**
  —— 用户 Mac 上 `~/.npmrc` 配了这条内网 Nexus，生成 lockfile 时被固化进去了。
- `storefront/package-lock.json` 是 **0 个**（干净），所以只有 admin 构建失败。
  **两个 lockfile 一比就知道问题在哪，这个对比很值。**
- 修法：只换 host 为 `https://registry.npmjs.org/`（路径本来就是标准 npm 布局，
  `integrity` 是内容哈希与下载地址无关，替换安全）。
- **`npm ci --registry` 对 tarball 是无效的**：它按 lockfile 的 `resolved` 下载（上面日志已证实）。
  要让它生效必须加 `--replace-registry-host=always`（npm 10 支持，默认值 `npmjs`）。
  已把这条加进两个 Dockerfile。
- **不要去改用户的 `~/.npmrc`**，那是他内网的配置，只报告。

## 买家端切换货币 bug 修复（本会话续做，已验证通过）

现象：买家端切货币类型不生效。修了三个独立的根因，**每个都要改对才算完**：

1. **standalone Next 15.1.6 的 `searchParams` 在运行时是 `undefined`**（即便声明 `force-dynamic`）。
   页面读 `sp.region` 直接 `TypeError` 抛 500。修法：所有页面/layout 用
   `regionFromSearchParams(await searchParams)` 兜底（空则 null，绝不抛）；
   真正的当前区域改由 **middleware 注入的 `x-neostore-region` 请求头** 承载
   （`server.ts` 里 `currentRegion` 优先读 header）。
2. **middleware 里 `request.cookies.get()` 也读不到入站 cookie**（解析后的 cookie
   store 是空的），但 `request.headers.get("cookie")` 里有。修法：自写
   `getCookie()` 从原始 `Cookie` 头正则解析。
   > **⚠️ 本条结论是错的，2026-09-16 已推翻**：`request.cookies.get()` 工作正常。
   > 当时两次调试都带着未定义的 cookie name（见下面第 3 点），才两次都失败。
   > 自写的 `getCookie()` 已删除。详见 `2026-09-16.md` 的「更正」一节。
3. **最阴的一个**：`REGION_COOKIE` 从 `"use client"` 的 `lib/session.ts` 导入进
   middleware（服务端）后运行时变成 `undefined` → 第 2 步的 name 永远不匹配。
   修法：新建 **`lib/constants.ts`（不带 `"use client"`）** 放 `REGION_COOKIE`，
   middleware / server / session 都从它取；session 仍 re-export 给客户端用。

链路：切货币 → `RegionSwitcher` 写 cookie + `router.push(?region=)` →
middleware 的 `regionParam` 分支把区域写进 `x-neostore-region` 头并回写 cookie →
server 组件读头定区域 → 价格按区域算。无 `?region=` 但有 cookie 的链接 →
`regionCookie` 分支 **307 重定向**到 `?region=`（不能用 rewrite，这里的 rewrite
会被静态预渲染吞掉区域，货币退回默认）。

验证（origin + 公网 `store.xiaodigua.shop` 都过）：
`?region=` 四个区各显对应币种（$19.99 / CN¥134.47 / €17.33 / ¥3,100）；
cookie-only → 307 → `?region=cn` → CN¥；所有路由 200，无 500；
详情页深链 cookie → €17.33。

### 两条可复用的 Next.js 教训（本仓库会再踩）
- **standalone 构建的 middleware/服务端别信 `searchParams` 和 `request.cookies.get`**：
  前者运行时 undefined，后者读不到入站 cookie；区域/状态这类 per-request 信息用
  middleware 注入的请求头传递最稳。
  > **⚠️ 后半句（`request.cookies.get`）是错的，2026-09-16 已推翻**：
  > 它读得到入站 cookie；真正的坑只有 cookie **name** 变成 `undefined`。
  > 前半句（`searchParams` 运行时 undefined）仍然成立。
- **服务端代码绝不能从 `"use client"` 模块导入值常量**：运行时会变 `undefined`。
  共享常量放一个不带 directive 的 `constants.ts`。

### 部署操作坑（已踩，照做）
- 沙箱挡 `~/.ssh/config`：ssh/scp 必须
  `-F /dev/null -o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no -i <pem>`。
- **scp 多文件到目录会拍平路径**：`lib/x.ts` 会落到 `src/x.ts` 而不是 `src/lib/x.ts`，
  必须逐个文件 scp 到精确目标路径，再 `rm` 误落的 stray 文件。
- 改完前端后：`docker compose build storefront && docker compose up -d --force-recreate storefront`，
  storefront 发布在 `127.0.0.1:3002`（公网走 `store.xiaodigua.shop`）。
